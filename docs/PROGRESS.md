## 2026-11-23 服务器端自动更新（推送即上线）

- **做法**：不引入 GitHub Actions，用服务器自己的 systemd timer 每 2 分钟检查一次 `origin/main`，有新提交就 `git reset --hard` → `docker compose build` → `up -d` → 探活。脚本 `scripts/server-autoupdate.sh`，单元 `xy-autoupdate.{service,timer}`（装在 `/etc/systemd/system/`）。
- **为什么不用 Actions**：仓库虽然是公开的（服务器能匿名 `git ls-remote`），但 Actions 要 SSH 到服务器，必须在 GitHub 里存 3 个 repo secret（host/user/key）。而服务器自己就能拉代码，等于少一层、少一堆密钥、也不烧 Actions 分钟。Actions 唯一的额外价值是「推送后立刻部署 + 有运行日志」；延迟由 2 分钟轮询顶上。
- **安全边界**：构建失败不重启旧容器（保留上一版）；`flock /tmp/xy-deploy.lock` 与 `scripts/deploy.ps1` 共用一把锁，手动部署与自动更新不会同时构建；`data/` 是 gitignore，`reset --hard` 不碰。
- **代价**：推送后最多 2 分钟才上线；若正好在抓取中被重启，那一轮抓取会中断（定时任务下一轮会补）。
- **已固化为流程**：AGENTS.md「部署」改成「默认只 push，不手动部署」，并写明只有需要立刻生效/紧急回滚才跑 `deploy.ps1`。线上实测：timer `active` + `enabled`，服务端 HEAD 与本地一致 `c3696d6`，journal 有「发现新提交 → 已上线 caddy=200」。

## 2026-11-23 已售出商品不再一直显示在售

- **现象**：¥1000 那件（`1101787649401`）用户在闲鱼看到「已售出」，站点 12:00 仍显示在售。
- **两个原因**：
  1. **时效**：收藏详情复检按 `favorites_minutes`（240 分钟）轮转，这件上次复检是 08:11，下次 12:11，12:00 看到的是 08:11 的状态——合理但会滞后。
  2. **真 bug**：售出后详情接口仍返回 `ret: SUCCESS`，只有 `itemDO.itemStatus = -2`；原逻辑只看 `ret` 里的「下架/删除」关键词，所以**永远不会**判失效。
- **修复**：`liveness.sold_reason()` —— `itemStatus < 0` 判失效（-2 记「已售出」，其余记「已下架」）；`parse_detail_price` / `parse_detail` / `check_liveness` 都接上，`DetailReading.dead_reason` 带到 `mark_dead()` 与 `sold` 事件里。
- **线上验证**：强刷该商品 → `dead=1, dead_reason=已售出`，事件 `已售出`。
- **提示用户**：点「立即运行」会立刻复检收藏，不必等 4 小时；想更勤可以在设置里调小收藏复检间隔。

## 2026-11-23 平台优惠价（挂牌价没动但实付更低）

- **现象**：Encore 那件挂牌 ¥3,400 一直不变，但买家实付 ¥1,700 —— 卖家用的是「平台优惠 减¥1,700」，不是改挂牌价，所以按 `soldPrice` 记录永远看不到降价。
- **接口事实**（线上抓的真实响应）：`itemDO.promotionPriceDO = {"promotionName":"活动价","promotionPriceMin":"1700.00","minDiscountFeeStr":"1700.00"}`，`soldPrice` 仍是 `3400`。之前探过的 CD 也有这个字段（94 → 活动价 93），说明是通用字段。
- **实现**：
  - `liveness._promo_price()` 从 `promotionPriceDO` 取最低有效价，**必须低于挂牌价**才算优惠；`DetailReading.promo_price` 带出。
  - `ItemRow.promo_price` / `list_price` 两列（已登记迁移）；`repo.set_promo_price()` 记录，优惠撤掉时清空。
  - `refresh_local_favorites` 按 **实付价 = min(挂牌, 优惠价)** 写观测与判断降价，事件理由写「平台优惠降价」。
  - DTO 带 `promo_price` / `list_price`；卡片在价格旁显示「平台优惠 · 挂牌 ¥3,400」（青色，与红色「已降」区分）。
- **线上实测**：强刷 Encore 那件 → `1700 / promo 1700 / list 3400 / reduce 1700`，事件 `平台优惠降价 3400.0 → 1700.0`。
- **口径说明**：`latest_price` 存的是**实付价**（优惠时按优惠价），因此走势与「已降」反映的是真实到手价；挂牌价单独存在 `list_price` 里。搜索接口不返回优惠价，所以只有「收藏详情复检」这条路能发现优惠。

## 2026-11-22 「有人降价了但我这边没更新」= 登录态过期

- **现象**：手动刷新后进度条一两分钟就消失，价格没变，「最后更新」还是几小时前；用户看到别人确实降了价。
- **定位**（线上探针抓原始响应）：搜索接口返回两条 —— `SUCCESS::调用成功`（但 **无 resultList**）和 **`FAIL_SYS_SESSION_EXPIRED::Session过期`**。即：**闲鱼登录态过期**，页面看着正常、列表永远为空，被代码当成「没人卖」。

## 2026-11-22 抓取「跑完却没更新」的排查

- **现象**：点「立即运行」后转圈消失，价格没变，「最后更新」还是几小时前，用户不知道是失败还是在跑。

- **实测**：修完在服务器上真跑一轮 → 约 8 分钟跑完，`watch_matches` 与 `price_history` 更新到 14:03，**记下 5 条降价事件**（如 ¥1,500 → ¥1,100、¥1,499 → ¥1,299），证明「搜索复看降价进事件流」也生效了。

## 2026-11-22 发布价与「已降价」

- **接口事实**（用真实登录态只读抓了一次）：搜索列表标签里有 `累计降价50%`（`fishTags.*.tagList[].data.content`），详情接口 `itemDO` 有 `originalPrice`（部分商品；门票类多为 `0`）和 `gmtCreate`（发布毫秒时间戳）。所以「已降多少钱」可以推出来：`最初挂牌价 ≈ 现价 / (1 - X%)`，再减去现价。
- **实现**：`Item.original_price`；`search._cumulative_original` 从标签反推；详情读到 `originalPrice > 0` 时用精确值覆盖（取较大者）。`ItemRow.original_price` 为新列（`migrate.py` 已登记）。首次写库或首次拿到原价时，用 `repo.seed_original_price` 在发布时间补一条观测作为走势起点；卡片价格旁显示「已降 ¥N」小字。
- **口径**：反推值是估算（平台按整数百分比四舍五入），与闲鱼搜索页自己显示的「已降 1501 元」同源；详情给的精确值优先。没被平台标注降价、或详情 `originalPrice=0` 的商品不会显示。

## 2026-11-22 条件内价格总览
